# TT-Lang + MLIR “как для дошкольников”, но правильно (00_ForKids)

## Зачем это читать

MLIR и компиляторные пайплайны часто “не похожи” на обычное программирование. Этот файл объясняет базовые идеи так, чтобы:

- быстро “врубиться” в смыслы слов (SSA, dialect, pass, lowering);
- не запутаться в деталях;
- при этом оставаться технически корректным.

Это не учебник — это **короткая правильная картинка в голове**.

## 1) Представь фабрику

Мы будем представлять MLIR как фабрику с коробками и станками.

### Коробки (values) и правило “один раз подписал”

- **SSA value** — это коробка с уникальной наклейкой, например `%0` или `%res`.
- Правило SSA: каждую коробку “подписывают” один раз (нельзя переписать наклейку). Если нужно новое значение — заводят новую коробку.

### Станки (operations)

- **Operation** — это станок: у него есть входные коробки, выходные коробки, и он делает преобразование.
- Станок всегда “говорит”, какие коробки он выдал (это и есть SSA значения).

### Форма коробок (types)

- **Type** — это правило формы/размера коробки: что внутри и какого “вида”.
- Тип важен: не каждый станок умеет принимать любую коробку.

### Наклейки-метки (attributes)

- **Attribute** — это наклейка на станке (или на функции), которая говорит компилятору “как именно” делать работу.
- Атрибут — не входная коробка. Это именно метаданные.

## 2) Комнаты и коридоры (regions/blocks)

Иногда на фабрике есть комнаты, внутри которых стоят станки:

- **Region** — это “комната с планом”.
- **Block** — это “участок” в комнате, куда можно зайти; у блока могут быть “входные коробки” (аргументы блока).

Это нужно, чтобы описывать вычисления с вложенными телами (например, compute-region), и control-flow.

## 3) Словари (dialects) и перевод (lowering)

### Dialect = словарь станков

**Dialect** — это “словарь”: какие станки вообще бывают и какие коробки/типы они понимают.

Например, в tt-lang встречаются диалекты вроде:

- TTL (удобные “высокоуровневые” станки для kernel-логики),
- TTKernel/EmitC (более “конкретные” уровни ближе к тому, что можно перевести в C++).

### Lowering = перевод на более конкретный словарь

**Lowering** — это как перевод сказки на язык с меньшим количеством слов:

- сначала можно говорить “сложными словами” (высокий уровень),
- потом нужно перевести в “простые и точные слова” (низкий уровень),
- чтобы дальше можно было сделать запуск/кодоген.

## 4) Роботы-редакторы (passes) и конвейер (pipeline)

### Pass = робот, который переставляет станки

**Pass** — это робот-редактор, который берет фабрику и переписывает план:

- заменить один станок на несколько других;
- добавить синхронизацию;
- упростить/почистить план.

### Pipeline = конвейер роботов (порядок важен)

**Pipeline** — это конвейер, где роботы идут в фиксированном порядке.

Порядок важен, потому что:

- робот №2 может ожидать, что робот №1 уже “приклеил наклейки” или “разложил детали”;
- если поменять порядок, робот №2 может не понять, что делать (и компиляция упадет).

## 5) Мини-сказка с настоящим MLIR (SSA + op + attribute)

Сюжет: “возьми два тайла, сложи, и пометь, в какой DST регистр это положить”.

```mlir
%a = "ttl.some_tile_source"() : () -> !ttcore.tile<32x32, bf16>
%b = "ttl.some_tile_source"() : () -> !ttcore.tile<32x32, bf16>
%r = ttl.tile_add %a, %b {dst_idx = 0 : i32} : !ttcore.tile<32x32, bf16>
```

Как читать:

- `%a` и `%b` — “коробки” (SSA values) с типом “тайл 32x32 bf16”.
- `ttl.tile_add` — “станок”, который берет две коробки и делает новую коробку `%r`.
- `{dst_idx = 0 : i32}` — наклейка-атрибут: “это вычисление связано с DST регистром 0”.

## 6) Как это связано с tt-lang (очень конкретно)

В tt-lang “история” обычно выглядит так:

1) Пишется Python kernel с потоками `@ttl.compute()` / `@ttl.datamovement()`.
2) Python frontend компилирует эти функции в **TTL IR** (диалект TTL).
3) Запускается **pipeline passes**, который переводит TTL в более конкретные формы (TTKernel, затем опционально EmitC).

Два полезных ориентира:

- Документ-трассировка: `docs/LOWERING_MULTITILE.md` (там видно “до/после” для каждого шага).
- Оптимизатор-драйвер: `ttlang-opt` (можно прогнать passes над MLIR, увидеть diagnostics).

## 7) Почему “вдруг упало” (3 типовых класса ошибок)

Когда что-то ломается, чаще всего это один из этих классов:

1) **Verification / type mismatch**: станок получил коробку “не той формы” (не тот type / не те атрибуты).
2) **Legality / conversion failed**: робот не смог перевести один станок в другой словарь (не хватает pattern’а).
3) **Unsupported op in translation**: уже на стадии “сделай C++” нашелся станок, который переводчик не умеет печатать.

Главная мысль: это не “магия”, а строгая цепочка преобразований. Если знать, где ты находишься (какой dialect/стадия), то причина обычно находится быстро.
