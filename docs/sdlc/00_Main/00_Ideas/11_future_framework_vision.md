# Видение фреймворка будущего (без ограничений)

## Контекст

Документ фиксирует целевое видение tt-lang как максимально удобного и гибкого фреймворка для разработки custom kernels: идеальный end-user код как источник требований к реализации, функциональный стиль и C++ ranges во внутренней реализации, модульность в духе PyTorch. Ограничения по версиям Python и C++ не учитываются; допускаются любые современные фичи.

Связанные документы:

- Текущие примеры: `examples/test_simple_add.py`, `examples/custom_dm_matmul.py`

## 1. Предпосылки и рамки

- **Нет ограничений**: любые версии Python и C++, любые языковые и библиотечные фичи.
- **Фокус**: максимально удобный и гибкий, модульный фреймворк; удобство разработки — приоритет.
- **Подход**: reverse-engineering — от «идеального» кода пользователя к требованиям к реализации. Сначала формулируется, как должен выглядеть и вести себя код пользователя; из этого выводятся контракты API и внутренняя архитектура фреймворка.

---

## 2. Целевой Python UX (end-user код)

Цель — аккуратный, понятный, структурированный финальный код пользователя. Если бы фреймворк уже предоставлял всё необходимое, сценарии вроде простого elementwise и matmul могли бы выражаться декларативнее и с меньшим boilerplate.

### 2.1 Сравнение с текущим состоянием

Сейчас в примерах:

- Явное задание `block_factors`, `grid` в декораторе и/или в теле; ручные проверки согласованности (assert M/K/N).
- Ручное создание `TensorAccessor(lhs)`, `TensorAccessor(rhs)` и явная передача CB/семафоров в каждую thread-функцию с дублированием сигнатур.
- Для matmul — явные циклы по k/m/n, ручное управление семафорами и mcast, разбор `core_index(0/1)` в DM.

Целевой UX:

- **Декларативность**: пользователь описывает, *что* делает kernel (операция, форма, политика памяти), а не все низкоуровневые параметры. Grid/block_factors по возможности выводятся из форм тензоров и политик.
- **Композиция из маленьких частей**: элементарные «модули» (один DM-шаг, один compute-шаг, один слой синхронизации) определяются отдельно и собираются в программу. В духе PyTorch: маленькие блоки, затем `Sequential` или явная сборка.
- **Минимум магии, максимум читаемости**: явная структура (имена, типы, контракты), без дублирования длинных списков параметров между compute и datamovement.
- **Единообразие**: один стиль для простых (add) и более сложных (matmul) кейсов — те же примитивы, те же паттерны композиции.

### 2.2 Пример целевого «идеального» сценария (иллюстрация)

Условный целевой вид для простого add (не спецификация, а направление):

- Описание операции и буферов на высоком уровне (например, «elementwise add», входы/выход, L1).
- Вызов одного билдера/декоратора, который по сигнатуре и метаданным тензоров собирает Program из DM + compute без явного перечисления всех CB в каждой функции.
- Для matmul — описание «tiled matmul» с указанием tiling/grid или их выводом; DM и compute описываются как композиция готовых примитивов (load tile, mcast, accumulate, store), а не как полностью ручные циклы и семафоры.

Итог: пользовательский скрипт короткий, структурированный, без дублирования; сложность сосредоточена в переиспользуемых примитивах фреймворка, а не в каждом скрипте.

## 3. Требования к реализации (reverse-engineering)

Из целевого UX следуют требования к фреймворку:

- **API**: декораторы/билдеры, которые принимают высокоуровневое описание (операция, формы, политики) и при необходимости выводят grid, block_factors, число CB и семафоров. Явное низкоуровневое API остаётся доступным для продвинутых сценариев.
- **Примитивы и композиция**: библиотека переиспользуемых «модулей» — элементарные DM-паттерны (load, store, mcast), compute-паттерны (elementwise, reduction, matmul tile), синхронизация. Пользователь собирает программу из этих кусков; фреймворк обеспечивает согласованные сигнатуры и подстановку в общую программу.
- **Инференс и валидация**: вывод параметров запуска и конфигурации из тензоров и опций; строгая валидация с понятными диагностиками при несовместимости.
- **Диагностика**: ошибки привязаны к месту в пользовательском коде и к этапу пайплайна (DSL → MLIR → passes); сообщения помогают быстро понять причину.

Реализация должна допускать пошаговое приближение: сначала покрываются простые кейсы (elementwise) с инференсом и композицией, затем более сложные (matmul, multi-core) на тех же принципах.

## 4. Функциональный стиль и изоляция

Проект про MLIR и преобразования — по сути про цепочки трансформаций над графами/IR. Это естественная область для более функционального стиля и чёткой изоляции.

### 4.1 Python

- **Трансформации и композиция**: фазы «исходный DSL → IR», «IR → IR» выражаются как композиция чистых (или явно ограниченных по побочным эффектам) шагов. Данные проходят по цепочке; каждый шаг тестируется отдельно на фиксированных входах.
- **Чистые фазы где возможно**: построение описания программы (например, граф операций, конфигурация CB) отделено от побочных эффектов (запись файлов, вызов runtime). Удобнее тесты и рассуждения о корректности.
- **Декларативные структуры**: конфигурация kernel/Program описывается структурами данных (dataclass, Pydantic и т.п.), а не только императивными вызовами; преобразования над этими структурами — функции «вход → выход».

### 4.2 C++

- **Ranges**: обход операций, блоков, аргументов в IR и в вспомогательных коллекциях — через `std::ranges` (или аналог), что уменьшает императивный шум (явные циклы, итераторы) и делает намерение «пройти, отфильтровать, преобразовать» явным. Лучшая читаемость и меньше мест для ошибок индексации.
- **Изоляция в passes**: логика одного pass по возможности изолирована: вход — IR/регион, выход — изменённый IR или результат; минимум глобального состояния. Упрощается юнит-тестирование и отладка.
- **Современный C++**: где уместно — алгебраические типы, optional/variant, инварианты типов для состояний IR; единообразная обработка ошибок (например, LogicalResult) без размазывания проверок по коду.

Итог: читабельность кода фреймворка растёт, многие ошибки локализуются в небольших, хорошо определённых функциях/преобразованиях.

## 5. Модульность в духе PyTorch

- **Сборка из модульных кусков**: операции, отдельные DM- и compute-шаги, примитивы синхронизации реализуются как отдельные, переиспользуемые единицы. Пользователь и фреймворк собирают из них программу (как в PyTorch собирают модель из модулей).
- **Понятный код пользователя и фреймворка**: финальный скрипт пользователя структурирован и короток; код фреймворка — такой же понятный и элегантный: чёткое разбиение по слоям (DSL API, билдеры, IR-генерация, passes, runtime), без гигантских монолитных файлов.
- **Тестируемость**: изолированные единицы — функции построения IR, отдельные преобразования, билдеры примитивов — легко покрываются тестами на фиксированных входах/выходах. Интеграционные тесты проверяют сборку цепочки и выполнение на устройстве/в симуляции.

Цель — не «всё в одном месте», а «каждый кусок делает одно дело и собирается в целое предсказуемо».

## 6. Не-цели и оговорки

- Этот документ — **видение и идеи**, а не пошаговый план внедрения. Конкретные решения (сроки, приоритеты, совместимость) остаются за отдельными задачами и ADR.
- **Совместимость с текущим API и миграция** не входят в scope данного видения; они могут быть темой отдельного плана при движении к целевому UX.
- Упоминание конкретных версий Python/C++ или библиотек (Pydantic, ranges и т.д.) иллюстративно; при реализации потребуется учёт реальных ограничений сборки и окружения.
