## Контекст

Документ фиксирует:

- **Примеры целевого кода** с точки зрения пользователя tt-lang: как может выглядеть текущая имплементация в виде короткого, понятного пользовательского кода.
- **Архитектурные изменения**, необходимые для поддержки такого кода.
- **План рефакторинга**: с чего начать (Python), затем C++; обновление стандартов и свободное использование современных фич; только влияние на архитектуру, без пошаговой имплементации.

Цель: **максимально гибкая система**, в которой пользователь коротко и понятно выражает желаемый алгоритм, а фреймворк сам корректно и оптимально распределяет вычисления по доступным ресурсам, исходя из нефункциональных требований (по умолчанию — low latency обработки всего объёма).

## 1. Примеры: как может выглядеть код с точки зрения пользователя tt-lang

Ниже — иллюстрации «как есть» vs «к чему стремиться». Синтаксис условный; цель — показать направление сокращения boilerplate и перенос решения о распределении на фреймворк.

### 1.1 Elementwise add (текущий стиль vs целевой)

**Текущий стиль** (упрощённо по `examples/test_simple_add.py`):

```python
@pykernel_gen(grid=(1, 1), block_factors=[(1, 1), (1, 1), (1, 1)])
def simple_add(lhs, rhs, out):
    lhs_accessor = TensorAccessor(lhs)
    rhs_accessor = TensorAccessor(rhs)

    @compute()
    def add_compute(lhs_cb, rhs_cb, out_cb):
        lhs_shard = lhs_cb.pop()
        rhs_shard = rhs_cb.pop()
        out_shard = out_cb.reserve()
        out_shard.store(lhs_shard + rhs_shard)
        out_cb.pop()

    @datamovement()
    def dm_lhs(lhs_cb, rhs_cb, out_cb):
        tx = dma(lhs_accessor[0, 0], lhs_cb.reserve())
        tx.wait()

    @datamovement()
    def dm_rhs(lhs_cb, rhs_cb, out_cb):
        tx = dma(rhs_accessor[0, 0], rhs_cb.reserve())
        tx.wait()
```

**Целевой вариант (иллюстрация)**:

Одна **программа** (unit пользовательского кода) может компилироваться в **один или несколько device kernels** (Reader, Compute, Writer и т.д.) в зависимости от решения планировщика. Именование `@ttl.program` подчёркивает именно это: пользователь описывает программу, фреймворк разбивает её на kernels.

```python
# Пользователь задаёт только семантику и формы; grid/CB/число потоков выводит фреймворк
@ttl.program  # или ttl.elementwise(add, memory="L1")
def add(lhs: ttnn.Tensor, rhs: ttnn.Tensor) -> ttnn.Tensor:
    return lhs + rhs  # фреймворк строит граф, раскрашивает по блокам, размещает (по умолчанию: low latency)
```

Вариант с явным указанием политики:

```python
@ttl.program(placement="auto", objective="latency")  # или "throughput", "balanced"
def add(lhs, rhs):
    return lhs + rhs
```

Архитектурный сдвиг: API принимает **декларативное описание** (операция + формы + опционально политика); построение Reader/Compute/Writer, CB, grid и конкретное размещение по топологии выполняет фреймворк (см. документ 12).

### 1.2 Tiled matmul (текущий стиль vs целевой)

**Текущий стиль** (сокращённо по `examples/custom_dm_matmul.py`): явные `block_factors`, `grid`, циклы по k/m/n, семафоры, mcast, `core_index`, два DM-ядра и один compute, ручной `Program(mm, dm0, dm1)(lhs, rhs, out)`.

**Целевой вариант (иллюстрация)**:

```python
@ttl.program
def matmul(lhs: ttnn.Tensor, rhs: ttnn.Tensor) -> ttnn.Tensor:
    return lhs @ rhs  # tiled matmul; tiling/grid выводится или задаётся опциями
```

С явным tiling и политикой:

```python
@ttl.program(tile=(32, 32), placement="auto", objective="throughput")
def matmul(lhs, rhs):
    return ttl.matmul(lhs, rhs, tile=(32, 32))
```

Архитектурный сдвиг: фреймворк владеет графом операций matmul (load tiles, mcast, accumulate, store); пользователь не пишет DM/compute вручную и не управляет семафорами; планировщик выбирает разбиение (в т.ч. отличное от фиксированного Reader-Compute-Writer), исходя из топологии и целевой метрики.

---

### 1.3 Цепочка операций (fused dropout + add)

**Целевой вариант**:

```python
@ttl.program
def fused_dropout_add(x, mask, bias):
    return ttl.dropout(x, mask) + bias  # один «граф»; фреймворк решает, сколько ядер и где резать
```

Пользователь описывает только порядок операций и зависимости; фреймворк строит разноцветный граф, сопоставляет блоки с ресурсами Tensix и размещает (возможно, в одном ядре или с разными Reader/Compute/Writer), минимизируя латентность или максимизируя throughput по умолчанию.

---

### 1.4 Явная композиция примитивов (продвинутый уровень)

Для тех, кто хочет контролировать стадии, но без ручного CB/семафоров:

```python
def my_kernel(a, b):
    load_a = ttl.primitives.load_tiles(a, buffer="L1")
    load_b = ttl.primitives.load_tiles(b, buffer="L1")
    comp = ttl.primitives.elementwise(load_a, load_b, op=operator.add)
    return ttl.primitives.store_tiles(comp)
```

Фреймворк по такой композиции строит граф с раскраской по блокам, проверяет контракты (форматы, CB/DST), и планировщик размещает примитивы на топологии; пользователь не задаёт grid и не пишет три отдельных @compute/@datamovement с полными сигнатурами.

---

### 1.5 Задание только нефункциональных требований

```python
@ttl.program(objective="latency")   # по умолчанию
def f(x, y):
    return x + y

@ttl.program(objective="throughput")
def g(x, y):
    return x * y
```

Один и тот же алгоритм может быть размещён по-разному в зависимости от `objective`; фреймворк выбирает стратегию размещения и при необходимости число «разрезов» (Reader-Compute-Writer vs ReaderCompute-Writer и т.д.) из модели из документа 12.

## 2. Архитектурные изменения (сводка)

Чтобы поддерживать такой целевой код, архитектура должна эволюционировать в следующих направлениях.

### 2.1 Слой описания алгоритма (Python)

- **Декларативное API**: операции и формы (и опционально tile, policy) без явного grid/CB/семафоров для типовых кейсов.
- **Построение графа операций**: из высокоуровневого описания строится внутренний граф (SSA/dataflow) с аннотациями ресурсов («цвет» блока: SFPU, FPU, NOC, unpack, pack и т.д.) — вход для планировщика из документа 12.
- **Композиция примитивов**: библиотека примитивов (load_tiles, elementwise, store_tiles, matmul_tile, mcast, …) с явными контрактами; компилятор переводит композицию в тот же граф с раскраской.
- **Нефункциональные параметры**: `objective` (latency / throughput / balanced), опционально `placement="auto"`; передача в планировщик как целевая метрика.

### 2.2 Планировщик и размещение

- **Вход**: раскрашенный граф (из 12), модель топологии (узлы, ресурсы, связи), текущее состояние устройств (или абстракция «доступно»).
- **Выход**: размещение (какая op на каком узле), расписание (порядок/времена), при необходимости решение о числе и границах ядер (RCW vs R-CW и т.д.).
- **Реализация**: детерминированный алгоритм (например, кратчайший путь / жадное размещение пучков) как первый этап; опционально в перспективе — эмулятор + RL (gymnasium) для политики распределения (см. 12).
- **Интеграция с компилятором**: результат планировщика материализуется в виде атрибутов IR / конфигурации ядер (grid, CB, семафоры, привязка потоков к стадиям), которые существующий lowering (TTL → TTKernel → …) уже умеет или будет уметь генерировать.

### 2.3 Слои компилятора (IR, passes, C++)

- **Layered IR**: явное представление контрактов ресурсов (CB/DST/NOC/SFPU/FPU) и, при необходимости, состояний устройств (см. 07_LLD_LayeredIR) — чтобы планировщик и верификация работали над одной моделью.
- **Passes**: отдельные фазы «построение графа с раскраской», «планировщик», «материализация размещения в IR»; данные между фазами — структурированные (граф, топология, план), не только «сырой» MLIR.
- **C++**: использование современного стандарта и фич (ranges, optional/variant, чистые функции там, где возможно) для читаемости и изоляции (см. видение 11); единообразная обработка ошибок (LogicalResult и т.п.).

### 2.4 Runtime и обратная связь

- **Вызов**: пользователь вызывает `program(lhs, rhs)` или `program(lhs, rhs, out)`; фреймворк по сигнатуре и тензорам строит граф, запускает планировщик, компилирует (с кэшем), выполняет.
- **Профилирование и метрики**: данные о реальных латентностях/загрузке (Tracy, device profiler) могут использоваться для уточнения модели топологии и весов «путей» в планировщике (см. 12, раздел 7). **Прикидки планировщика**: в первую очередь получать из бенчмарков в **tt-sim** (симулятор должен хорошо реплицировать тайминги и работу hardware); дополнительно — тайминги на больших конфигурациях (несколько карт), в т.ч. на реальном HW.

## 3. План рефакторинга (только влияние на архитектуру)

Рефакторинг ведётся так, чтобы в итоге можно было писать целевой код из раздела 1. План задаёт порядок и области изменений без пошаговой имплементации.

### 3.1 Начать с Python

- **Приоритет 1 — описание и граф**: ввести структуры данных для «алгоритма» (набор операций, формы, зависимости, опционально примитивы). Не обязательно сразу полный декларативный `lhs + rhs`; достаточно явной композиции примитивов (пример 1.4) с построением графа операций и раскраской по типам ресурсов. Это даёт точку интеграции для планировщика.
- **Приоритет 2 — политики**: добавить в конфиг/декоратор параметры `objective` и `placement`; пробросить их в следующий слой (пока можно игнорировать в планировщике-заглушке).
- **Приоритет 3 — упрощение текущего API**: по возможности выводить grid/block_factors из форм и политик для простых кейсов (elementwise), сохраняя обратную совместимость с явной передачей.
- **Тесты**: каждый шаг сопровождать тестами (построение графа, сериализация/десериализация, совпадение с ожидаемым IR для регрессий).

### 3.2 Затем C++

- **Стандарт и фичи**: зафиксировать минимальный стандарт (например, C++20) и свободно использовать ranges, optional/variant, concepts там, где это упрощает обход IR и трансформации. Обновить стиль кода (LLVM/проект) под новый стандарт.
- **Изоляция и читаемость**: passes, работающие с графом и топологией, писать в функциональном стиле (вход → выход, минимум глобального состояния); обходы коллекций — через ranges, где уместно.
- **Планировщик в C++**: когда модель топологии и графа стабилизирована на Python, перенести или продублировать ядро планировщика (например, Dijkstra-подобное размещение пучков) в C++ для скорости и интеграции с MLIR passes; Python может оставаться точкой входа для описания алгоритма и вызова компиляции.

### 3.3 Совместно

- **Документация состояний устройств (mermaid)**: вести описание состояний и переходов (CB, DST, семафоры, ядра) в mermaid (или аналоге), согласованное с кодом и IR; использовать как источник истины для верификации и для планировщика (см. 12).
- **Совместимость**: сохранять возможность писать «по-старому» (явные @compute/@datamovement и grid) для продвинутых сценариев; новый декларативный путь — опция по умолчанию для типовых ops.

## 4. Итог

- **Примеры (раздел 1)** показывают, как может выглядеть код пользователя tt-lang: от «одна строка» add/matmul до явной композиции примитивов и задания только `objective`. Во всех случаях фреймворк берёт на себя построение разноцветного графа и распределение по ресурсам (по умолчанию — low latency).
- **Архитектурные изменения (раздел 2)** — декларативное API, граф с раскраской, планировщик поверх топологии и state-машины устройств, layered IR и современный C++ — обеспечивают возможность такой гибкой системы.
- **План рефакторинга (раздел 3)** задаёт порядок: сначала Python (граф, политики, упрощение API), затем C++ (стандарт, ranges, планировщик), при постоянной опоре на документы 11 и 12. Имплементация деталей остаётся за отдельными задачами; здесь зафиксировано только влияние на архитектуру и целевой код пользователя.
