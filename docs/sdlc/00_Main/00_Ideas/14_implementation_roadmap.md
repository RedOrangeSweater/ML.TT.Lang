- В документации видения (13): все примеры целевого кода с `@ttl.program`; явное пояснение «одна программа → один или несколько kernels».

- Семантика не меняется; бэкенд тот же (pykernel_gen).

## Фаза 3: Построение графа операций (внутреннее представление)

- Ввести внутреннее представление «программа как граф операций»: узлы — операции (elementwise, load, store, matmul_tile, …), рёбра — зависимости по данным; аннотации по ресурсам (тип блока: SFPU, FPU, NOC, …) — «раскраска» по документу 12.
- Для текущих программ, описанных через @compute/@datamovement: при компиляции строить этот граф **после** существующего фронта (AST → TTL IR); граф строится из TTL IR или из промежуточного представления, согласованного с 06/12.
- Пока не менять решение о числе kernels (Reader-Compute-Writer остаётся фиксированным); граф используется для логирования, тестов и подготовки к планировщику.
- Критерий: для simple add и одного дополнительного примера граф строится и сериализуется (например, в тест); узлы и рёбра соответствуют ожидаемым операциям и зависимостям.

## Фаза 4: Заглушка планировщика и топология

- Ввести минимальную модель топологии (узлы = ядра, ресурсы на узле, связи) по документам 06/08; параметризация под текущий grid (прямоугольник).
- Реализовать заглушку планировщика: вход — граф операций + топология, выход — «план» (размещение каждой op по узлам), при этом план **жёстко** воспроизводит текущее поведение (один compute + два DM, фиксированный grid). Цель — пройти весь путь «граф → план → материализация в IR» без изменения результата компиляции.
- Материализация плана: атрибуты IR (grid, привязка потоков к стадиям) заполняются из плана; существующий lowering (TTL → TTKernel) по возможности не меняется или меняется минимально.
- Тесты: результат компиляции и выполнения для simple add (и одного multicore примера) не меняется при включённой заглушке планировщика.

## Фаза 5: Упрощение API для простых кейсов (вывод grid / block_factors)

- Для элементарных программ (например, один elementwise add с одинаковыми формами входов/выхода): выводить `grid=(1, 1)` и `block_factors` из форм тензоров, если пользователь не задал их явно.
- Сохранять возможность явной передачи; при конфликте (задано и выведено) — явное значение имеет приоритет или ошибка валидации.
- Документировать в спецификации/примерах; тесты на вывод для 1–2 сценариев.

## Фаза 6: Декларативный слой (опционально) — «одна строка» add

- Экспериментальный API: описание вида «return lhs + rhs» внутри `@ttl.program` без явных @compute/@datamovement; фронт переводит это в граф операций (одна elementwise op + load/store), затем в текущую схему (1 compute + 2 DM) через кодогенерацию или шаблон.
- Реализация может быть ограничена одним типом (add, float32, фиксированный tile); цель — доказать жизнеспособность пути «декларативное описание → граф → текущий backend».
- Тесты: один пример «одна строка add» компилируется и выполняется; результат совпадает с ручным simple add.

## Фаза 7: Планировщик с альтернативными разбиениями

- Расширить планировщик: учитывать `objective` (latency/throughput) и выдавать план, который может отличаться от фиксированного RCW (например, меньше kernels, другой баланс DM/compute).
- Требует: метрики или оценки стоимости (латентность, throughput) для кандидатов; валидация плана (ресурсы, протоколы CB/DST) перед материализацией. **Источник прикидок**: бенчмарки в **tt-sim** (симулятор должен хорошо реплицировать тайминги и поведение hardware); дополнительно — тайминги на больших конфигурациях (несколько карт), в т.ч. на реальном HW, для калибровки модели (см. документ 12).
- Критерий: для хотя бы одного примера планировщик выдаёт план, отличный от RCW, и компиляция/выполнение остаются корректными (с тестом на совпадение результата с эталоном).
