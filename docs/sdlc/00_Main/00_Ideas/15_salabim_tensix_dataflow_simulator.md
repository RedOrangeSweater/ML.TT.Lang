## Контекст

В проекте **ShopsSimilarity** (`/home/kilka/Projects/ML/ShopsSimilarity`) есть рабочие salabim-версии симулятора для задачи нескольких магазинов: фабрики производят несколько товаров (каждая свой набор), ингредиенты по рецептам (BOM), машины (грузовики) возят между фабриками и магазинами, магазины продают финальную продукцию. Сущности: Factory, Store, Truck, Batch, VisualEvent, рецепты (ingredients → product).

Идея: **взять эту модель за основу** и реализовать симулятор, в котором:

- **Tensix-cores** отображаются **слабо на фоне** (контекст топологии).
- **Основной упор**: **разноцветные вычислительные блоки** (умеют вычислять: SFPU, FPU, unpack, pack, NOC/DMA) и **разноцветные блоки — DataFlow states** (состояния потока данных), которые **требуют конкретное вычисление** в данный момент эволюции пучка DataFlow.

Связь с документом 12: раскрашенный граф, Tensix как «фабрики», state-машина устройств; здесь — конкретная реализация визуального/дискретно-событийного симулятора на salabim по аналогии с цепочкой поставок.

## Маппинг ShopsSimilarity → Tensix/DataFlow

| ShopsSimilarity | Tensix/DataFlow симулятор |
|-----------------|----------------------------|
| **Фабрика** (производит сырьё) | **Разноцветный вычислительный блок** (SFPU, FPU, unpack, pack, NOC): умеет выполнять операцию своего «цвета»; потребляет входы/состояния, производит результат/новое состояние. |
| **Магазин** (потребляет ингредиенты по рецепту, производит продукт) | **Разноцветный блок — DataFlow state**: в данный момент эволюции пучка данных **требует** конкретное вычисление (какой «цвет» блока должен обработать этот пучок); после выполнения пучок переходит в следующее состояние. |
| **Грузовик** (возит между фабриками и магазинами) | **NOC/DMA** или дуга графа: перенос данных между блоками (перемещение пучка DataFlow между вычислительными блоками/состояниями). |
| **Партия (Batch)** (единица товара в очереди/транзите) | **Пучок DataFlow** (tile / dataflow-единица): движется по графу, в каждом узле имеет «текущее состояние» (какое вычисление требуется). |
| **Рецепт (BOM)** (какие ингредиенты → продукт) | **Зависимость операции**: какое вычисление (какой цвет блока) должно быть выполнено над пучком в данном состоянии; «ингредиенты» — входные слоты/буферы, «продукт» — результат в DST/CB. |

Tensix-ядра в этой модели — **слабый фон**: например, сетка или набор слабо выделенных зон, на которой размещены разноцветные блоки; визуально ядра не доминируют, акцент на «цветах» вычислений и состояний пучков.

## Визуализация

- **Фон**: сетка/карта Tensix-cores (приглушённые прямоугольники или зоны), без детализации подсистем ядра — только контекст размещения.
- **Разноцветные вычислительные блоки**: прямоугольники или «фабрики» с цветом по типу ресурса (SFPU, FPU, unpack, pack, NOC); подпись типа; при занятости — индикатор (какой пучок обрабатывается).
- **Разноцветные DataFlow state блоки**: блоки другого визуального ряда (например, ромбы или слоты), цвет = какое вычисление **требуется** в этот момент для пучка; подпись — тип требуемой операции или слот DST/CB.
- **Пучки DataFlow**: движущиеся объекты (аналог грузовиков с грузом), переносятся между блоками; при попадании в state-блок «заказывают» вычисление у блока соответствующего цвета, затем переходят в следующее состояние.

События (аналог VisualEvent в ShopsSimilarity): «вычисление начато», «вычисление завершено», «пучок перешёл в состояние», «перенос по NOC» — можно подсвечивать цветами по типу операции.

## Реализация

- **База**: скопировать или форкнуть структуру ShopsSimilarity (salabim, `sim.Component`, очереди, позиции, `AnimateRectangle`/`AnimateText` и т.д.), заменить доменную модель (фабрики/магазины/грузовики) на модель «вычислительные блоки + DataFlow state блоки + пучки».
- **Сущности** (по аналогии с `entities.py` / `entities_refactored.py`):
  - `ComputeBlock(sim.Component)` — вычислительный блок с полем `block_type` (цвет): SFPU, FPU, unpack, pack, NOC; очередь входов или слоты; процесс «выполняет операцию» и отдаёт результат в следующий блок или в очередь пучков.
  - `DataFlowStateBlock(sim.Component)` — блок-состояние: какой тип вычисления **требуется** для пучка в этом узле; хранит или ссылается на «рецепт» (какая операция, какие входы/выходы); при появлении пучка формирует «заказ» на вычисление у ComputeBlock нужного цвета.
  - `DataFlowBundle(sim.Component)` — пучок данных (аналог Batch): перемещается по графу, имеет текущее состояние (в каком DataFlowStateBlock находится, какое вычисление требуется); после обработки переходит в следующее состояние или в следующий узел.
  - `DataMover(sim.Component)` — аналог Truck: переносит пучки между узлами (NOC/DMA); может быть общий «транспорт» или дуги графа с задержкой.
- **Конфиг**: топология (сколько ядер, как размещены), набор ComputeBlock по цветам, граф DataFlowStateBlock и дуг между ними, рецепты (какое состояние → какое вычисление → следующее состояние).
- **Размещение**: Tensix-cores задаются координатами или сеткой; на них размещаются ComputeBlock и DataFlowStateBlock; пучки и «транспорт» движутся по дугам с задержками (латентность NOC, время вычисления).

Цель: получить работающий salabim-симулятор с визуализацией, где на фоне слабо видны ядра, а на первом плане — разноцветные вычислительные блоки и разноцветные DataFlow state блоки с эволюцией пучков. Далее модель можно использовать для отладки планировщика, подбора прикидок (латентность, throughput) и согласования с документом 12.
