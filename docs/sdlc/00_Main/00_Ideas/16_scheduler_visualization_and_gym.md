## Контекст

Документ фиксирует видение: **React 3D UI** для визуализации и отладки планировщика (без редактирования кода) и **движок как Gymnasium environment** для итеративного/обучаемого поиска маппинга «алго-граф → HW-топология». Целевая модель — **динамическая система** (в духе AlphaStar): разные стратегии размещения приводят к разному поведению во времени — одни буферы («гаражи») заполняются, другие пустуют; одни вычислительные блоки («фабрики») всё время заняты, другие долго ждут ресурсов или не используются. Reward и сравнение стратегий (в т.ч. RCW vs найденный план) должны опираться на **прогон динамики**, а не только на статическое размещение.

## 1. Цель и границы

**Цель**: дать визуальный «дебаггер» планировщика и движок для итеративного/обучаемого поиска маппинга «алго-граф → HW-топология».

**Границы**:

- **UI**: только просмотр и управление воспроизведением (шаг / итерация / полный запуск); редактирование кода и графа — вне скоупа первой версии.
- **Движок**: формализация как Gymnasium env: state = граф + топология + текущий плейсмент; action = размещение блока; reward = метрика качества маппинга/латентности.
- **Источники данных**: граф операций и топология экспортируются из tt-lang (op_graph, topology, schedule_stub); HW-топология с расстояниями (L1/CB vs NOC/LAN) — конфиг или замер при старте, либо упрощённая модель.

---

## 2. Динамика и метрики (целевая модель без упрощений)

**Placement задаёт игру; динамика — это сама игра.** Выбранная стратегия размещения задаёт начальную конфигурацию; после этого разворачивается **динамика** (поток данных, очереди, занятость ресурсов). Разные стратегии приводят к разному поведению во времени: какие буферы заполняются, какие фабрики заняты или простаивают.

**Состояние системы во времени** (для симулятора и для env):

- **Буферы/очереди**: уровень заполнения по каждому буферу (CB, слоты DST), очередь пучков на входе/выходе блоков (док. 12, 15).
- **Фабрики (compute-блоки)**: занят/свободен, время до завершения текущей операции, очередь ожидающих пучков.
- **Пучки данных** (Batch/tile): текущее местоположение (в каком блоке/очереди), в каком состоянии DataFlow (какое вычисление требуется дальше) — по док. 15.
- **События во времени**: «вычисление начато/завершено», «пучок перешёл», «буфер заполнен/опустошён» — для логирования и для reward.

**Метрики качества стратегии** (из динамики, не из статики):

- Утилизация фабрик (доля времени занятости), разброс по фабрикам (одни перегружены, другие простаивают).
- Латентность прохождения пучков по графу (время от входа до выхода).
- Bottlenecks: буферы, которые часто полные или часто пустые при голодании потребителя; фабрики с длинной очередью или длительным ожиданием входа.
- Пропускная способность (throughput): сколько пучков в единицу времени завершило путь.

**Источник метрик**: прогон симулятора динамики (док. 15 — salabim, фабрики/магазины/грузовики/партии → compute/DataFlow/NOC/пучки) или упрощённая дискретная модель (очереди, задержки по рёбрам, занятость блоков). Reward в Gymnasium env — функция от траектории динамики и/или от агрегированных метрик после прогона, а не от одного лишь статического placement.

## 3. UI-видение

**Три вида**:

1. **Вертикальный граф алго-нод** — построенная фреймворком вычислительная структура (узлы-примитивы алгоритма, рёбра — зависимости).
2. **Вид по ресурсам** — переключение на сеть минимальных ресурсов FPU/SFPU/NOC с раскраской по типу (документ 12).
3. **HW-представление** — «на полу» как сеть городов с расстояниями: ядра/узлы топологии, связи с lat/bw; как алгоритм ищет маппинг и к чему приводит разбиение на kernels с общением по NOC (Reader-Compute-Writer или найденный вариант).

**Управление и отладка**:

- Пошаговое воспроизведение (шаг), итерация планировщика или полный запуск.
- Индикатор прогресса (%) и пояснение «почему алгоритм пошёл сюда».
- Сравнение двух планов side-by-side (например RCW vs найденный) — доказательство, что RCW менее эффективен.
- Синхронный пошаговый запуск нескольких конфигураций (разный folding исходного графа на HW).

Интерфейс только для просмотра и отладки, без редактирования кода.

## 4. Gymnasium-постановка

**Два уровня**: (1) **Фаза размещения** — по графу и топологии выбираем placement (текущий env); (2) **Фаза динамики** — по готовому placement запускаем симулятор (док. 15 или упрощённая модель), собираем метрики по траектории; reward и сравнение стратегий — по этим метрикам (утилизация, латентность, bottlenecks), а не только по статическому placement. Без прогона динамики сравнение «RCW vs найденный план» не полное: нужно показать разное поведение во времени (какие буферы полные, какие фабрики простаивают).

**Environment (фаза размещения, текущая реализация)**:

- **State**: op graph (узлы, рёбра, op_type, resource), topology (сетка + опционально lat/bw), текущий placement (node_id → core).
- **Action**: назначить очередную op на core (или пошаговое назначение в порядке топологической сортировки).
- **Step**: обновление placement, вычисление reward, done (все узлы размещены).
- **Reward**: заглушка — минус сумма «расстояний» по рёбрам графа (статическая оценка); целевой источник — **прогон динамики** (док. 15): утилизация фабрик, латентность пучков, bottlenecks, throughput. Текущий reward остаётся заглушкой до подключения симулятора.

**Два пути решения**:

- **Эмуляция/статистика**: в runtime собирать статистику, пускать эмуляцию, двигать алго-ноды между compute-нодами, выделять bottlenecks и скопления/разрежения.
- **Infer по модели**: обучать на многих синтетических примерах (близких к реальности, на основе реальных); определять что-то вроде «угол-расстояние» между алго-нодами по аналогии с предсказанием структуры белка; infer размещение по графу и топологии.

**HW-топология**: на старте — замер (ping/bandwidth между узлами) или конфиг: L1/CB = быстрые, NOC = средние, LAN = медленные (в т.ч. кластер 100x100 м). Передаётся в env и в UI как граф «городов с расстояниями».

**Связь с док. 12 и 15**: док. 12 задаёт state-машину устройств, CB/DST состояния, «фабрики» по типам ресурсов (SFPU, FPU, NOC), маршрутизацию пучков — динамическая модель должна явно представлять эти состояния во времени. Док. 15 (salabim) реализует движок динамики: при заданном размещении симулятор выдаёт траекторию заполнения буферов, занятости фабрик, движения пучков; эту траекторию используют для reward и визуализации в UI.

## 5. Интерфейс данных (экспорт из tt-lang)

Единый JSON для UI и env:

- **op_graph**: nodes (id, op_type, resource, predecessors, successors), явные рёбра или выводимые из predecessors/successors.
- **topology**: grid_cols, grid_rows; опционально: lat/bw между парами ядер или по типу связи (L1/NOC/LAN).
- **plan**: placement (node_id → [col, row]), grid_cols, grid_rows.

Функция/скрипт в tt-lang: `export_scheduler_input(program, grid)` или аналог, выдающий такой JSON (файл или поток).

## 7. Риски и допущения

- **Риски**: (1) 3D-визуализация может быть тяжёлой — рассмотреть 2.5D или уровни детализации; (2) HW-топология в кластере требует замеров/конфига, в MVP достаточно параметризуемой модели; (3) обучение «AlphaFold-подобной» модели — отдельная большая задача; (4) полноценный симулятор динамики (salabim по док. 15) — отдельный объём работ; допустим поэтапный путь: сначала упрощённая дискретная динамика (очереди, задержки), затем замена на salabim.
- **Допущения**: формат графа и топологии расширяем; lat/bw в первой версии — конфиг или константы по типу связи (L1/NOC/LAN). AlphaStar-подобное обучение (много стратегий, отбор по итогам игры) — отдельное направление; план ограничивается уточнением модели (динамика + метрики) и интерфейса env/simulator.
