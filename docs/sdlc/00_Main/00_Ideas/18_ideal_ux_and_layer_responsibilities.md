# 18: Идеальный UX и разделение ответственности (user / framework / engine)

- **Статус**: draft.
- **Цель**: зафиксировать целевой код «без ограничений» и из него реверсить, что делает пользователь, фреймворк и движок.

## 1. Идеальный код (как бы выглядел код без ограничений)

Программист думает только «что считать» и «куда / с какими параметрами». Всё остальное (grid, треды, CB, дескрипторы) — за фасадом.

```python
# IDEAL: одна строка запуска
ttl.run(add_kernel, lhs, rhs, out, grid=(2, 2))

# IDEAL: spec как данные (если нужна явность)
spec = ttl.Spec(program=add_kernel, grid=(2, 2), memory="L1")
ttl.run(spec, lhs, rhs, out)

# Внутри run: один конвейер — spec → compile → run.
# Никаких декораторов, Program(threads)(args), ручной сборки request'ов в голове пользователя.
```

Один фокус при чтении: в пользовательском файле — только описание kernel и вызов run (или Spec + run).

## 2. Кто что делает (реверс из идеального кода)

| Роль | Ответственность |
|------|------------------|
| **Пользователь** | Описывает «что считать» (kernel / program) и «с какими параметрами запустить» (grid, memory, опции). Не думает о CB, типах тредов, дескрипторах. |
| **Фреймворк** | Spec (Pydantic), фасад `run(spec, *args)` или `run(program, *args, grid=..., )`. Маппинг пользовательского намерения в единый request (KernelCompileRequest и т.д.). Валидация, опции, консистентность слоёв. |
| **Движок** | Компиляция (MLIR, passes), размещение (граф, планировщик — в т.ч. паттерны вроде Reader/Compute/Writer как внутренняя деталь), запуск (дескрипторы, device). Не экспонирует MLIR, граф, типы тредов в верхний API. |

Reader/Compute/Writer — один из паттернов размещения внутри движка, а не имена слоёв, которые обязан знать пользователь.
