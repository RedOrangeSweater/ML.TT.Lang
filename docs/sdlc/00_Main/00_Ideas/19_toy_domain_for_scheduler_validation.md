## Контекст

Сразу решать задачу Tenstorrent сложно: много сущностей, алгоритмы на ней тестировать и валидировать трудно. Цель — спроектировать систему так, чтобы её **легко можно было настроить** на **Toy example**: задачу, аналогичную планировщику, но переформулированную в домене, где:

- Легко генерировать экземпляры задач.
- Для части экземпляров **известно оптимальное решение** (валидация алгоритмов).
- Удобно тестировать систему в целом, в том числе на **performance** (бенчмарки планировщика и симулятора без железа).

Варианты Toy domain по степени «близости к товарам»:

1. **Абстрактный**: магазины, товары, BOM (bill of materials), фабрики со «сферой» (какие операции умеют).
2. **Ближе к товарам**: пекарни — мука, печи, хлеб; рецепты (BOM), доставка, очереди заказов.

Один и тот же планировщик (граф задач, ресурсы, топология, целевая метрика) работает поверх **абстрактной модели**; подставляется либо «слой Tenstorrent» (ядра, SFPU/FPU/NOC, латентности), либо «слой Toy» (магазины, пекарни, грузовики, рецепты). Так алгоритмы размещения и симулятор проверяются на простых и контролируемых примерах.

## 1. Зачем Toy domain

- **Валидация**: на экземплярах с известным оптимумом проверять, что планировщик (RCW, Дейкстра, A*, MCTS и т.д.) находит правильное или близкое к правильному решение.
- **Отладка**: маленькие и читаемые экземпляры (несколько «магазинов», несколько «операций») — быстрая итерация без устройства.
- **Performance**: бенчмарки планировщика и симулятора на тысячах экземпляров Toy (генерация, один прогон, сравнение алгоритмов) без зависимости от Tenstorrent.
- **Обучение/RL**: среда Gymnasium может быть реализована сначала для Toy domain (пространство состояний и действий проще), затем тот же интерфейс — для Tenstorrent.

## 2. Общая абстрактная модель (единая для Tenstorrent и Toy)

Чтобы один и тот же планировщик и симулятор работали и на Tenstorrent, и на Toy, вводится **общий слой абстракции**:

| Понятие | Tenstorrent | Toy (магазины/BOM) | Toy (пекарни) |
|--------|-------------|--------------------|---------------|
| **Ресурс (узел)** | Ядро Tensix (SFPU, FPU, NOC, …) | Фабрика / магазин (тип: производитель/потребитель) | Пекарня, склад, печь |
| **Операция (задача)** | Вычисление (add, load, store, …) | «Произвести/доставить товар по рецепту» | «Испечь хлеб», «доставить муку» |
| **Зависимости** | Граф данных (тайл → операция → тайл) | BOM: какие товары/ингредиенты → продукт | Рецепт: мука + печь → хлеб |
| **Топология** | Сетка ядер, латентность/пропускная способность NOC | Граф: фабрики и магазины, дороги (время/пропускная способность) | Граф: пекарни, склады, маршруты |
| **Пучок (единица работы)** | Тайл / dataflow-единица | Партия товара (Batch) | Заказ (булка, батон) |
| **Целевая метрика** | Латентность, throughput, утилизация | Время выполнения заказов, загрузка фабрик | Время оборота заказов, загрузка печей |

Контракт: планировщик получает **граф операций** (узлы с типами ресурсов, рёбра — зависимости), **топологию** (узлы-ресурсы, веса рёбер), **целевую метрику**; возвращает **план размещения** (какая операция на каком ресурсе/узле). Источник «графа» и «топологии» — либо Tenstorrent (из Program/IR), либо **генератор Toy** (магазины, BOM, пекарни).

## 3. Toy domain: уровни конкретики

### 3.1 Уровень 1: Магазины, товары, BOM, фабрики (абстрактный)

- **Сущности**: товары (типы), фабрики (каждая умеет производить подмножество товаров), магазины (потребляют товары по «рецептам»), BOM (какие товары → какой продукт).
- **Ресурсы**: узлы графа — фабрики и магазины; рёбра — «дороги» (время доставки, пропускная способность).
- **Задачи**: «доставить партию товара A в магазин M», «произвести на фабрике F продукт P по BOM».
- **Генерация**: случайный граф (N фабрик, M магазинов, K типов товаров, BOM заданы); можно генерировать экземпляры, для которых жадный или полный перебор даёт известный оптимум.

### 3.2 Уровень 2: Пекарни (ближе к товарам)

- **Сущности**: мука, вода, печь, хлеб, булка; пекарня (имеет печи, рецепты), склад (ингредиенты), магазин (заказы).
- **Рецепты (BOM)**: хлеб = мука + вода + 1 цикл печи; булка = мука + 2 цикла печи и т.д.
- **Ресурсы**: узлы — пекарни (с числом печей), склады, магазины; рёбра — маршруты (время, грузоподъёмность).
- **Задачи**: «испечь 10 булок в пекарне P», «доставить муку со склада S в пекарню P».
- **Генерация**: фиксированный набор рецептов, случайная сетка пекарен/складов/магазинов; экземпляры с маленьким графом — известный оптимум (ручной или полный перебор).

Оба уровня дают **одну и ту же абстрактную модель** (граф операций + топология + метрика), поэтому один планировщик и один симулятор могут работать с обоими.

## 4. Генерация Toy-экземпляров и известный оптимум

- **Случайная генерация**: параметры (число узлов, число типов товаров/операций, плотность BOM, веса рёбер) задаются конфигом или RNG; генерируется граф задач и топология. Подходит для массового тестирования и бенчмарков performance.
- **Экземпляры с известным оптимумом**:
  - Вручную задать маленький граф (2–3 фабрики, 2 магазина, один BOM) и посчитать оптимальное расписание (полный перебор или жадный с доказательством).
  - Специальный генератор: строить задачу «от ответа» — задать целевой план и сгенерировать граф/топологию, для которых этот план оптимален (валидация: планировщик должен найти тот же или эквивалентный план).
- **Регрессионные тесты**: зафиксировать набор Toy-экземпляров (и при необходимости эталонные планы) в репозитории; при изменении алгоритмов планировщика проверять, что качество/оптимум не ухудшается.

## 5. Настройка системы на Toy

- **Конфиг домена**: выбор бэкенда — `tenstorrent` | `toy_shops` | `toy_bakeries`. От него зависят: генератор графа и топологии, симулятор (salabim-модель магазинов/пекарен или Tensix/DataFlow), метрики (время оборота заказов vs латентность ядра).
- **Единый вход планировщика**: граф операций (узлы с типами ресурсов) + топология (узлы-ресурсы, веса рёбер) + опции (objective: latency / throughput / balanced). Планировщик не знает, откуда пришёл граф — из tt-lang Program или из генератора Toy.
- **Симулятор**: один интерфейс «состояние + план → траектория + метрики»; реализации — для Tenstorrent (упрощённая или salabim по док. 15) и для Toy (магазины/пекарни, salabim по аналогии с ShopsSimilarity). Визуализация может переключаться: либо «ядра + блоки», либо «карта магазинов/пекарен».
- **Gymnasium env**: один контракт (state, action, reward, done); внутри — либо Tenstorrent, либо Toy. Обучение и отладка политик сначала на Toy (быстро, много эпизодов), затем перенос на Tenstorrent при необходимости.

## 6. Структура по папкам/модулям (предложение)

- **Общая модель** (не зависит от домена): граф операций, топология, план размещения, целевая метрика — типы и интерфейсы; планировщик (алгоритмы) принимает только эти абстракции.
- **Backends**:
  - `tenstorrent/` — построение графа и топологии из Program/IR; симулятор Tensix/DataFlow (или заглушка).
  - `toy_shops/` — генератор «магазины + BOM + фабрики», топология графа магазинов; симулятор salabim (магазины, грузовики, партии).
  - `toy_bakeries/` — генератор «пекарни + рецепты + склады»; симулятор salabim (пекарни, печи, заказы).
- **Тесты и бенчмарки**: `test/scheduler/toy/` — генерация экземпляров, экземпляры с известным оптимумом, регрессия; `benchmarks/scheduler/` — прогон планировщика на тысячах Toy-экземпляров (performance).

## 7. Итог

- Систему планировщика и симулятора проектировать так, чтобы **один и тот же контракт** (граф + топология + метрика → план) работал и для Tenstorrent, и для Toy domain.
- Toy domain: **магазины/товары/BOM/фабрики** (абстрактный) и **пекарни** (конкретный) — одна абстрактная модель, два уровня конкретики.
- **Генерация** Toy-экземпляров (случайная и «с известным оптимумом») для валидации алгоритмов и регрессий.
- **Performance-тесты** планировщика и симулятора на Toy без железа; при необходимости — переключение конфига на Tenstorrent для тех же алгоритмов.
