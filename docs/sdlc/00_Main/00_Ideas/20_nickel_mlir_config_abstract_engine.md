## 1. Nickel для конфигурации абстрактного движка

### 1.1 Что задаётся в Nickel (типизированно, модульно)

- **backend**: `tenstorrent` | `toy_shops` | `toy_bakeries` (как в док 19 §5). От него зависят: генератор графа и топологии, симулятор, метрики.
- **graph**: либо ссылка на источник (Program/IR, путь к генератору), либо параметры генератора Toy (число узлов, типы товаров/операций, BOM; см. док 19 §4).
- **topology**: узлы-ресурсы, рёбра, веса (латентность/пропускная способность); для Toy — граф магазинов/пекарен и «дорог», для Tenstorrent — сетка ядер и NOC.
- **objective**: `latency` | `throughput` | `balanced` (как в ProgramOptions/planning).
- Опционально: **опции симулятора** (salabim, упрощённая модель), **опции планировщика** (алгоритм, лимиты).

### 1.2 Преимущества Nickel

- Типы и контракты в одном месте; переиспользование фрагментов (например, общая схема топологии).
- Экспорт в JSON/YAML для существующих пайпов (загрузка в Python/Pydantic, интеграция с CI).
- Возможность импорта стиля LLK DB v2 (как в prompts-search) для контрактов ресурсов Tenstorrent; для Toy контракты проще (BOM, типы узлов).

### 1.3 Связь с док 19

Конфиг домена (док 19 §5 «Настройка системы на Toy») и выбор бэкенда задаются этим Nickel-конфигом; генераторы Toy и построение графа из Program читают параметры из конфига.

## 2. MLIR-слой для валидации конфигураций

### 2.1 Назначение

Проверять **консистентность и контракты** конфига абстрактного движка до запуска планировщика/симулятора (без привязки к домену в IR).

### 2.2 Вариант A (лёгкий)

- **Nickel → JSON/YAML** → загрузка в Python/Pydantic.
- Валидация через Pydantic и отдельные проверки: связность топологии, соответствие BOM (для Toy), допустимость backend и objective.
- MLIR для конфига не используется. Минимальный старт; подходит для Toy и для быстрой итерации.

### 2.3 Вариант B (слой MLIR)

- Ввести небольшой **config dialect** в MLIR (или использовать существующий общий слой), кодирующий: backend, схему графа (узлы, типы ресурсов), схему топологии (узлы, рёбра, веса).
- Nickel (или код) экспортирует конфиг в этот диалект; pass **config-verify** проверяет: допустимость backend, связность топологии, соответствие графа контрактам (для Toy — BOM, для Tenstorrent — контракты LLK по 07_LLD).
- Единый verifier для обоих доменов за счёт абстрактных контрактов (требования/эффекты узлов). Целевой вариант, если потребуется единая валидация с остальным MLIR-пайплайном (07_LLD L2/L3) и общий «source of truth» для контрактов.

### 2.4 Рекомендация

В документе описаны **оба варианта**; Вариант A — минимальный старт (Nickel + Pydantic); Вариант B — целевой при необходимости интеграции с MLIR-пайплайном и контрактами LLK.

## 4. Структура по файлам (при реализации)

- **Nickel-схемы**: например `config/scheduler/` или `config/abstract_engine/` в tt-lang — типы и фрагменты Nickel для backend, graph, topology, objective; при необходимости подкаталоги `toy/`, `tenstorrent/` с импортами из общей схемы.
- **Валидация**: при Варианте A — Pydantic-модели в Python (например в `ttl/scheduler/` или `ttl/config/`), загрузка из JSON/YAML; при Варианте B — MLIR dialect и pass в tt-lang (или tt-mlir), вызов из пайплайна или отдельной утилиты.

Реализацию (Nickel-файлы, Pydantic-загрузка или MLIR dialect) выполнять после согласования дизайна.
