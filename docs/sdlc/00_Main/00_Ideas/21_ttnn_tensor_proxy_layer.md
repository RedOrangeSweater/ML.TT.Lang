# Слой прокси для тензоров ttnn (идея)

**Статус:** идея, не утверждённая спецификация.

## Суть

Вынести «реальное использование ttnn» в отдельный слой: все типы, которые сейчас зависят от `ttnn.Tensor`, проксировать в типы, определённые в tt-lang. Остальной код опирается только на эти типы; наличие или отсутствие установленного ttnn не влияет на проверки типов. Валидацию (что маппинг корректен) выполнять только при инициализации: если ttnn установлен — проверить, что зарегистрированный тип (например, `ttnn.Tensor`) реализует ожидаемый интерфейс; если ttnn нет — проверку не делать.

## Цели

- **Без зависимости от ttnn в коде:** компиляция, тесты без устройства, типопроверка не требуют `import ttnn`; проверки вида «это тензор рантайма» идут через наши типы/протокол.
- **Один слой, который знает про ttnn:** только этот слой регистрирует `ttnn.Tensor` как реализацию нашего протокола и при загрузке (при наличии ttnn) проверяет соответствие интерфейсу.
- **Валидация только при инициализации:** при старте (или первом импорте слоя) при установленном ttnn — проверить, что у `ttnn.Tensor` есть нужные методы (device, memory_config и т.д.); при отсутствии ttnn — не выполнять проверку.

## Подход

1. **Протокол (или ABC) в tt-lang:** например, `RuntimeTensor` с методами `device()`, `memory_config()` — минимум того, что нужно для detect_memory_space, is_interleaved и запуска ядра.
2. **Регистрация реализаций:** слой (например, `runtime_tensor` или расширение `ttnn_proxy`) при загрузке при наличии ttnn добавляет `ttnn.Tensor` в список зарегистрированных типов «рантайм-тензор» и опционально вызывает валидацию (проверка наличия методов протокола у `ttnn.Tensor`).
3. **Единая точка проверки:** вместо `is_ttnn_tensor(x)` (и `isinstance(x, ttnn.Tensor)`) использовать `is_runtime_tensor(x)` — проверка по зарегистрированным типам; при отсутствии ttnn список пуст, функция возвращает False.
4. **Типы только у нас:** в аннотациях и контрактах использовать наш протокол/тип, а не `ttnn.Tensor`; слой границы с ttnn при необходимости кастует/оборачивает только при вызове ttnn API.

## Связь с текущим кодом

- Сейчас: `dtype_utils.is_ttnn_tensor` делегирует в `runtime_tensor.is_runtime_tensor`; при недоступности ttnn список типов пуст, возвращается False.
- Для нового кода предпочтительно использовать `is_runtime_tensor` из `ttl.runtime_tensor` (или из `ttl`); `is_ttnn_tensor` из `dtype_utils` — алиас для обратной совместимости.

## Открытые вопросы

- Нужен ли явный wrapper (обёртка над `ttnn.Tensor`) или достаточно регистрации типа и протокола (ttnn.Tensor считается реализующим протокол)?
- Где именно держать валидацию при инициализации: отдельный модуль `runtime_tensor` с `register_runtime_tensor_type` и вызовом при импорте, или внутри существующего `ttnn_proxy`?
