# Архитектура TT-Lang — Низкоуровневый дизайн: Симулятор

## 0. Метаданные

- **Статус**: Актуально (LLD).
- **Аудитория**: разработчики симулятора/моделей планирования и авторы kernels, которым нужен воспроизводимый прогон без железа.
- **Цель**: определить, что именно считается корректностью в симуляторе и где проходит граница "функциональная модель" vs "временная модель".
- **Связанные документы**:
  - `docs/sdlc/00_Main/02_Architecture/03_LLD_RuntimeAndPythonAPI.md` (контракт исполнения)
  - `docs/sdlc/00_Main/02_Architecture/05_LLD_Testing.md` (тесты симулятора)

## 1. Назначение

Этот документ описывает симулятор tt‑lang: зачем он нужен, где расположен, какие подсистемы моделирует и как он связан с DSL/пайплайном.

Симулятор полезен когда:

- нет железа,
- нужно проверить корректность логики управления CB/pipes,
- нужно собрать “приближённые” метрики и сравнить стратегии планирования,
- нужно воспроизводить сценарии без долгого цикла сборки/запуска.

## 2. Где расположен код

- Python симулятор: `python/sim/`
- Тесты симулятора: `test/sim/`

## 3. Что именно моделируется (уровни точности)

В рамках текущей реализации (и этого LLD) фиксируется **функциональная** симуляция.

Временные/контеншн модели могут существовать как отдельные экспериментальные инструменты, но они не считаются частью текущей архитектуры `docs/01_Architecture`.

### 3.1 Функциональная симуляция (Python `python/sim/*`)

Цель: запускать kernels, написанные под compiler API, на симуляторном backend **без изменений исходников**.

Ключевой механизм: launcher подменяет импорты `ttl` и `ttnn` на симуляторные реализации.

- Launcher: `python/sim/ttlang_sim.py` (исполняется через `ttlang-sim`)
  - делает `sys.modules["ttl"] = sim.ttl` и `sys.modules["ttnn"] = sim.ttnn` (shadowing).
- Симуляторные реализации API/моделей:
  - CB/протоколы: `python/sim/cb.py`, `python/sim/cbapi.py`, `python/sim/cbstate.py`
  - Program/планировщик: `python/sim/program.py`
  - Tensor модель: `python/sim/ttnnsim.py`

#### 3.1.1 Модель исполнения: cooperative scheduler + yield-инструментация

В `python/sim/program.py` используется подход:

- исходный Python код thread-функций преобразуется: перед блокирующими действиями (wait/reserve) вставляется `yield (cb, operation)`,
- scheduler выполняет генераторы в round-robin,
- если генератор "блокируется" (по контракту CB), scheduler переключается на другой,
- если блокируются все - детектируется deadlock и формируется диагностируемая ошибка.

Это архитектурно важно, потому что:

- симулятор может воспроизводимо находить нарушения протокола CB (overflow/underflow, invalid reserve/wait),
- симулятор дает точку наблюдаемости, которая намного дешевле, чем прогон на железе.

#### 3.1.2 Инварианты и ограничения функциональной модели

- **Цель**: корректность протоколов (CB/pipes/semaphores) и детекция deadlock.
- **Не цель**: cycle-accurate моделирование вычислений или NOC (в этой ветке).
- **Детерминизм**: предполагается детерминированный порядок планирования (round-robin) при фиксированном коде и начальном состоянии; недетерминизм пользовательского Python (например, случайность) остается на совести теста.

## 4. Связь с pull‑based и профилированием

Этот раздел является опциональным: симулятор может использоваться как “песочница” для экспериментальных политик планирования/профилирования. Эти материалы не считаются частью основной документации; если требуется, их можно держать в отдельных design-notes (вне `docs/01_Architecture`).

## 5. Типовые ошибки и ограничения

- симулятор может быть не цикл‑точным,
- симулятор может не моделировать все конфликтующие ресурсы,
- переносимость результатов требует калибровки по железу.

### 5.1 Как валидировать симулятор (практическая стратегия)

- **Функциональная ветка**: валидируется через `test/sim/`:
  - positive tests: корректное завершение без deadlock и без CBContractError,
  - negative tests: гарантированная диагностика при нарушении контракта (overflow/underflow/invalid reserve/wait).
- **Временная ветка**: валидируется не "корректностью вывода", а консистентностью метрик и чувствительностью к latency параметрам:
  - sanity: рост `dma_read_lat` должен ухудшать utilization compute при отсутствии prefetch,
  - regression: сценарии должны сохранять относительный порядок стратегий при фиксированных задержках.

## 6. Точки расширения

- добавить новые примитивы (CB, pipe, semaphore) в модель,
- добавить больше ресурсов/каналов NOC,
- добавить сбор метрик (stall breakdown) и экспорт “строк прогона” для embedding.
